# P4 측정 결론 (2026-09-07, 1차)

측정: `node eval/run.mjs` — 프로파일 2종(mid=규칙+리포맵, light=규칙+리포맵+파일 원문) ×
모델 2단계(haiku=경량 대리, sonnet=중간 대리) × 과제 3종. 원자료는 `results.md`
(러너가 매 실행 덮어씀).

| | haiku | sonnet |
|---|---|---|
| **mid** (리포맵만, ~210tok) | 2/3 | 2/3 |
| **light** (파일 포함, ~500tok) | **3/3** | **3/3** |

## 결론

1. **실패를 가르는 것은 모델 등급이 아니라 컨텍스트 형태였다.** 구현 세부(q2:
   할인 배율)는 sonnet도 리포맵만으로는 못 맞혔고, haiku도 파일 원문이 있으면
   맞혔다. 두 모델 모두 mid에서 같은 문제를 틀리고 light에서 전부 통과.
   → 저성능 모델 지원의 핵심은 "더 좋은 모델"이 아니라 **light 팩(파일 원문
   포함)을 기본 제공**하는 것. 프로파일 설계의 존재 이유가 실측으로 확인됨.
2. **리포맵은 구조 질문(어느 파일에 무엇이 있나)을 최약체 모델에서도 해결**한다
   (q1 전원 통과, ~210토큰). 구조 탐색 용도로는 mid가 가장 싸다.
3. **주의**: q3(호출 관계)은 리포맵에 호출 정보가 없는데도 두 모델이 시그니처와
   이름으로 추론해 통과했다. 이름이 좋은 코드베이스에서만 성립하는 요행이며,
   근거 없는 추론(환각) 위험 지점 — 리포맵만 주고 호출 관계를 묻는 사용은
   피하고, 필요하면 Tier 3(search_symbol/Serena)를 쓰게 할 것.
4. **예산 튜닝**: 이 픽스처 규모에서 light 팩은 ~500토큰으로 기본 예산(12,000)에
   크게 못 미침 — 기본값 유지. 튜닝이 의미를 갖는 건 실제 규모 저장소에서
   target-files가 예산에 잘릴 때이므로, 실전 저장소 온보딩 후 재측정.

## 2차: 실전 저장소 재측정 (2026-09-07)

`node eval/run.mjs --fixture <실전 저장소> --tasks <과제.yaml> --module risk`
(소스 308개 실전 저장소, 원자료는 로컬 보관(비공개 저장소 식별 정보 포함)):

| | haiku | sonnet |
|---|---|---|
| mid (규칙+리포맵, ~4.3k tok) | 2/3 | 2/3 |
| light (risk 모듈 팩, ~8.7k tok) | **3/3** | **3/3** |

- 픽스처 결론이 실전 규모에서 그대로 재현됨: 구현 세부(q2: pdm 기본
  정비주기 180일)만 mid에서 실패, light에서 전 모델 통과.
- 이 측정이 결함 2건을 드러내 수정함: ① 팩이 캐시된 8k 리포맵을 통째로
  삽입해 target-files 예산을 굶기던 것 → 섹션 캡(budget/3, 최대 4k),
  ② target-files 알파벳 순서로 뒤쪽 파일이 잘리던 것 → 참조 랭킹 순 배치.
  수정 전에는 pdm.py가 팩에서 탈락해 q2가 전 셀 실패였음.
- 두 모델 모두 mid에서 "컨텍스트에 없다"고 정직하게 답함(환각 없음).
- 예산 튜닝 결정: light 12k 유지(랭킹 상위로 충분), 모듈 전체가 필요한
  128K급 로컬 모델용으로 해당 저장소에 light-xl(45k) 프로파일 추가.

## 3차: 실전 저장소 실사용 검증 (2026-09-07)

실전 저장소에서 실제 Claude Code 세션(`claude -p --mcp-config .mcp.json`,
파일 읽기 도구 차단)을 띄워 신규 개발자 시나리오 3문항 수행:

- **결과: 3/3 전부 정답, 4턴, 9.3초.** 에이전트는 `get_rules` →
  `search_symbol(maint_interval_days)` 단 2회의 ctxkit 호출로 해결.
- 프론티어 프로파일 설계(최소 규칙 상시 + 온디맨드 검색)가 실사용에서
  그대로 나타남 — 벌크 팩(light ~8.7k tok) 없이 두 번의 표적 호출로 충분.
  같은 질문을 light 팩으로 풀던 경량 모델 경로와 대비되는, 계층 설계의
  실증 사례.
- search_symbol의 참조 라인 출력에 파라미터 기본값
  (`maint_interval_days: int = 180`)이 그대로 실려 세부 질문까지 해결됨 —
  정의+참조를 함께 주는 출력 형식의 부수 효용 확인.

## 4차: 모듈 범위 맵 도입 후 재측정 (2026-09-07)

팩 동작을 세 가지 바꾼 뒤(모듈 팩의 맵을 모듈 범위로 축소, 예산 초과 파일을
중단이 아니라 건너뛰기, 모듈 밖 상위 파일의 경로 색인 추가) 2차와 동일한
매트릭스를 재실행했다.

| 과제 | mid | light | 판정 |
|---|---|---|---|
| q1 심볼 위치(모듈 **밖** `his.py`) | 0/2 | 0/2 | **설계상 정상** |
| q2 구현 세부(모듈 안 `pdm.py`) | 0/2 | **2/2** | 2차와 동일 |
| q3 규칙 | 2/2 | 2/2 | 2차와 동일 |

**q1은 회귀가 아니라 경계의 확정이다.** 같은 질문을 `--module` 없이 저장소
전체 팩으로 물으면 **4/4 전원 통과**(mid ~4.2k tok, light ~12.0k tok)한다.
즉 모듈 팩은 모듈 밖 심볼의 정의 위치를 답할 수 없고, 저장소 전체 팩은 답한다.
경로 색인이 `services/twin/twin/clients/his.py`의 **존재**는 알려주지만
심볼 개요는 담지 않으므로, 네 모델 모두 추측 대신 "컨텍스트에 없다"고
답했다 — 바람직한 실패 방식이다.

실무 규칙으로 정리하면:
- 모듈 팩은 **그 모듈 안의 작업**을 위한 것이다. 과제·질문도 모듈 안으로
  한정할 것.
- 모듈 밖 심볼 위치는 `search_symbol`(3계층) 또는 `--module` 없는 팩으로.
- 이 변경으로 얻은 것: 모듈 팩의 맵에서 무관한 파일 4개 제거, 대상 파일
  4개 → 13개(예산 사용률 55% → 99%).

## 5차: 추출기 수정 후 무회귀 확인 (2026-09-07)

기획 v2.2 검토 중 추출기 결함을 발견해 고쳤다 — 타입 주석이 붙은 const
(`export const fn: Handler = (x) => x`)가 **전혀 추출되지 않아** TS 파일의 참조
크레딧이 누락되고 있었다. 랭킹이 바뀌므로 [AGENTS.md](../AGENTS.md) 제약대로 4차와
동일한 매트릭스를 재실행했다.

**결과: 4차와 완전히 동일**(mid 1/3·1/3, light 2/3·2/3, q1은 모듈 팩 설계상 실패).
twin의 상위 랭킹도 불변(his.py, scenarios_p2.py, models.py). ctx-kit 자신에서는
심볼 0개 파일이 3→2로 줄고 `symbols.ts`가 상위로 올라왔다 — TS 비중이 큰
저장소일수록 효과가 크다는 뜻이다.

### 기획 검토를 위한 부수 측정 (모델 호출 없음)

v2.2 명세를 계산 가능한 형태로 만들기 위해 시제품으로 얻은 수치:

- **중복 심볼 필터 체인** — twin: 129 → 56(테스트 제외) → 30(최상위 정의만) →
  26(4자↑·던더 제외) → **12(시그니처 동일)**. 남은 12건에 실제 중복이 있다
  (`secret`·`hmacHex`가 route/session/middleware 3파일에 재정의). ctx-kit 자신은
  정확히 1건(`escapeRegExp`가 mcp.ts·repomap.ts). "최상위 정의만"이 절반을
  걷어내는 최강 필터인데 **추출기에 들여쓰기 정보가 없다** → `topLevel` 필드 필요.
- **고아 파일 오탐률** — twin: 308 → 93(외부 참조 0) → 30(테스트 제외) →
  **19(엔트리포인트 제외, 6%)**. ctx-kit: 19 → 3(16%). 단, **심볼 0개로 추출된
  파일은 고아로 판정하면 안 된다**(추출 실패와 미사용이 구분 불가; twin 22/308).
- **성능 기준선** — 308 소스 저장소에서 전체 팩 2.6초, 맵 1.5초. §6-B 성능 예산의
  출발점.

## 6차: 무료 지표가 모델 실측을 재현한다 (2026-09-07)

`ctxkit eval --dry-run`이 모델을 한 번도 부르지 않고 계산한 포함률과, 4차에서
모델로 얻은 결과를 대조했다.

| 팩 | outline_hit | content_hit | 4차 모델 실측 |
|---|---|---|---|
| 모듈 팩(risk), mid | 1/2 (50%) | 0/2 (0%) | q1 실패·q2 실패 |
| 모듈 팩(risk), light | 1/2 (50%) | **1/2 (50%)** | q1 실패·**q2 통과** |
| 저장소 전체 팩, mid | 2/2 (100%) | 0/2 (0%) | q1 통과·q2 실패 |
| 저장소 전체 팩, light | 2/2 (100%) | 1/2 (50%) | q1·q2 모두 통과 |

**셀 단위로 일치한다.** 모듈 팩에서 모듈 밖 심볼(q1)은 outline 미적중이고 모델도
못 맞혔으며, 저장소 전체 팩에서는 둘 다 적중·통과다. 구현 세부(q2)는 content가
있어야만 통과한다. 즉 **모델 호출 없이 프로파일 선택을 판정할 수 있다** —
§4.1이 목표한 바가 실측으로 확인됐다.

### 그 과정에서 지표 자체의 결함을 하나 고쳤다

초기 구현은 `outline_hit`을 "리포맵 섹션에 경로 문자열이 포함되는가"로 판정했다.
모듈 팩은 모듈 밖 파일을 **경로만** 나열하는 방향 색인을 담으므로, 이 판정은
`his.py`를 적중으로 세어 mid를 2/2(100%)로 보고했다 — 그러나 4차 실측에서 모델은
같은 조건에서 **0/4로 답하지 못했다**. 경로 한 줄로는 "어디에 정의됐나"에 답할 수
없기 때문이다. 판정을 "심볼 개요를 가진 `## <경로>` 제목이 존재하는가"로 조이자
위 표처럼 모델 결과와 일치하게 됐다.

교훈: **지표는 그것이 예측한다고 주장하는 실측과 대조해야 한다.** 대조 없이는
느슨한 문자열 매칭이 능력을 과대평가하는 것을 알 수 없다.
