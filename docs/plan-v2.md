# ctx-kit 기획 v2 — 과제 형태의 컨텍스트

> 대상 버전: v0.3.0 · 작성 2026-09-07 · 선행 문서: [ai-context-plan.md](ai-context-plan.md)(체계),
> [package-architecture.md](package-architecture.md)(패키지), [WHITEPAPER.ko.md](WHITEPAPER.ko.md)(설계·측정)
>
> v1(0.1.0~0.2.1)에서 확정된 것: 4계층 컨텍스트, 3중 인터페이스, 능력 프로파일,
> npm 공개 배포, 실전 저장소 온보딩 1건, 측정 3라운드. 이 문서는 **그 다음 한 걸음**을
> 설계한다.

---

## 1. 진단 — v1이 답하지 못하는 질문

측정([findings.md](../eval/findings.md)) 전 라운드에서 성패를 가른 것은 하나였다:
**필요한 파일이 팩 안에 있었는가.**

- q2(구현 세부)가 통과한 이유: `pdm.py`가 참조 랭킹 1위여서 **우연히** 들어갔다.
- q1(모듈 밖 심볼)이 실패한 이유: `his.py`가 모듈 밖이라 들어가지 않았다.
- 4차 측정에서 확정된 경계: 모듈 팩 0/4 vs 저장소 전체 팩 4/4.

즉 v1의 선별 기준은 **정적이고 과제와 무관**하다. "이 저장소에서 중요한 파일"에는
답하지만 "지금 하려는 일에 필요한 파일"에는 답하지 않는다. 사용자는 항상 특정
과제를 들고 오는데, 컨텍스트는 매번 같은 것을 준다.

두 번째 진단: **규칙 계층(Tier 0)의 부패를 아무도 검사하지 않는다.** `check`는
규칙이 짧은지·동기화됐는지만 본다. 규칙이 *아직 사실인지*는 검사 대상이 아니라,
경로가 사라지거나 명령이 바뀌는 순간 시스템 전체가 조용히 거짓말을 시작한다.
Tier 0은 모든 프로파일에 주입되므로 부패의 파급이 가장 크다.

## 2. v2가 추가하는 설계 원칙

기존 6원칙(백서 §3)에 두 가지를 더한다.

7. **컨텍스트는 과제 형태를 띤다.** 같은 저장소·같은 프로파일이라도 무엇을 하려는지에
   따라 다른 파일이 담겨야 한다. 선별 기준은 `중요도`에서 `중요도 × 과제 관련도`로
   확장된다.
8. **도구 수는 늘리지 않는다.** MCP 도구는 5종을 유지하고 기능은 파라미터로 넓힌다.
   에이전트에게 선택지를 늘리는 것은 비용이며, 도구가 늘수록 잘못 고를 확률이 는다.

## 3. 항목별 설계

### 3.1 질의 기반 팩 — `--about`

**문제.** 사용자는 "할인 계산을 고쳐줘"라고 말하지만 팩은 저장소 상위 파일을 준다.

**인터페이스.**

```sh
ctxkit pack --about "gold tier 할인 배율" [--profile light] [--module risk]
ctxkit pack --about "SMART 인증 폴백" --stdout | ollama run qwen3:14b
```

MCP는 도구를 늘리지 않고 `make_pack`과 `get_module_context`에 선택 파라미터
`about`을 추가한다.

**알고리즘.** 기존 참조 점수에 질의 점수를 곱이 아닌 **가중합**으로 더한다(곱은
질의와 무관한 핵심 파일을 0으로 만들어 방향 감각을 잃게 한다).

```
terms   ← 질의를 공백으로 분리, 2글자 미만·불용어 제거, 소문자화
q(F)    ← Σ_t [ 4·(경로에 t 포함) + 3·(심볼명에 t 포함) + 1·min(본문 내 t 출현, 10) ]
score(F) ← normalize(ref(F)) + 2 · normalize(q(F))
```

정규화는 각 점수를 해당 집합의 최대값으로 나눈다(0~1). 가중치 2는 초기값이며
3.6의 실측으로 조정한다. 질의가 없으면 v1과 동일하게 동작한다(회귀 없음).

**구현 지점.** `core/repomap.ts`의 `rankFiles(config, files?)`에 세 번째 인자
`query?: string`를 추가하고, `core/pack.ts`의 `targetFiles`가 이를 전달한다.
팩 헤더에 `about="…"`를 기록해 산출물이 스스로를 설명하게 한다.

**검증.** 과제 세트마다 "정답이 들어 있는 파일"을 명시하고 **포함률**(정답 파일이
팩에 포함된 비율)을 측정한다. 목표: `--about` 사용 시 포함률 ≥ 90%, 미사용 대비
상승. q1류(모듈 밖 심볼) 과제가 `--about`으로 회복되는지도 확인한다.

**리스크.** 질의어가 코드에 없는 자연어(예: "결제가 느려요")면 질의 점수가 0에
가까워 v1과 같아진다 — 이는 안전한 열화다. 한국어 질의는 형태소 분석 없이는
부분 일치가 어려우므로, 초기 구현은 부분 문자열 일치를 허용한다.

**규모.** 반나절.

### 3.2 규칙 부패 탐지 — `check`의 새 항목

**문제.** AGENTS.md가 존재하지 않는 경로나 더 이상 안 도는 명령을 가리켜도 게이트가
통과한다. 규칙은 모든 프로파일에 들어가므로 거짓말의 파급이 가장 크다.

**인터페이스.**

```sh
ctxkit check                # 경로·글롭 검증 포함(기본)
ctxkit check --run-commands # 문서화된 명령을 실제 실행(옵트인)
```

**알고리즘.**

1. AGENTS.md의 백틱 구간을 추출한다.
2. `/`를 포함하거나 알려진 확장자로 끝나면 **경로 후보**로 보고 존재를 확인한다
   (글롭은 매치 0건이면 실패). 존재하지 않으면 `fail` — 규칙이 거짓이 됐다는 뜻이다.
3. `## Commands` 섹션 안에서 알려진 러너(`npm`,`pnpm`,`yarn`,`pytest`,`cargo`,`go`,
   `make`,`docker`,`uv`,`poetry`)로 시작하면 **명령 후보**로 본다. 기본은 존재
   검증만(러너가 PATH에 있는가 → `warn`), `--run-commands`일 때만 실행한다
   (타임아웃 120초, 비영점 종료는 `fail`).
4. `context.config.yaml`의 모듈 글롭이 **매치 0건**이면 `fail`(설정 부패). 리팩터링
   후 모듈 경계가 깨진 것을 잡는다.

부작용이 있는 명령을 자동 실행하지 않기 위해 3은 옵트인이며, `## Commands` 밖의
백틱은 명령으로 취급하지 않는다.

**구현 지점.** `core/check.ts`에 `rule-rot`·`config-rot` 검사 추가. 실행은
`node:child_process`의 `spawnSync`.

**검증.** 픽스처에 부패를 인위 주입(경로 삭제, 글롭 무효화)해 100% 검출을 확인하고,
ctx-kit·twin 두 실전 저장소에서 오탐 0을 확인한다.

**리스크.** 백틱 안 코드 조각을 경로로 오인할 수 있다 — 확장자·슬래시 조건과
"파일명처럼 보이는가" 휴리스틱으로 좁히고, 오탐 시 `check`가 실패하므로 초기에는
경로 검사도 `warn`으로 시작해 실전 오탐률을 본 뒤 `fail`로 승격한다.

**규모.** 반나절.

### 3.3 변경 중심 팩 — `--diff`

**문제.** 리뷰·수정 작업의 컨텍스트는 "저장소에서 중요한 것"이 아니라 "방금 바뀐
것과 그것에 닿는 것"이다.

**인터페이스.**

```sh
ctxkit pack --diff HEAD~3          # 리비전 범위
ctxkit pack --diff --staged        # 커밋 직전 검토
ctxkit pack --diff origin/main...  # PR 범위
```

**알고리즘.** 시드 = `git diff --name-only <범위>`의 소스 파일. 확장 = 시드가 정의한
심볼을 참조하는 파일(참조 랭킹 상위 N=10). 출력 순서는 시드 전부 → 확장 순이며,
시드는 예산을 초과해도 잘리지 않고 **경고와 함께 전부 포함**한다(변경 파일이 빠진
리뷰 컨텍스트는 무의미하다). 헤더에 범위와 시드 목록을 기록한다.

**구현 지점.** 새 모듈 `core/git.ts`(diff 목록, 저장소 여부 판별), `core/pack.ts`에
시드/확장 경로. git 저장소가 아니면 명확한 오류를 낸다.

**검증.** 변경 파일 포함률 100%, 확장 파일이 실제 호출자인지 표본 확인. twin의 최근
커밋 3건으로 팩을 만들어 토큰량과 유용성을 육안 확인.

**리스크.** 거대한 diff(마이그레이션 대량 변경)에서 시드만으로 예산을 초과할 수
있다 — 이때는 시드 목록만 경로로 나열하고 원문은 상위 랭킹만 담는 열화 모드로
전환한다.

**규모.** 반나절.

### 3.4 공변경 랭킹 — git 이력을 신호로

**문제.** 정적 참조는 import·호출이 있는 결합만 본다. 실제로는 "같이 고치게 되는"
파일이 더 유용할 때가 많다 — 설정과 코드, 스키마와 마이그레이션, 문서와 구현처럼
참조 관계가 없는 결합이 그렇다.

**인터페이스.** 설정으로 켠다(기본 꺼짐 → 실측 후 기본값 결정).

```yaml
ranking:
  cochange: true      # git 이력 기반 공변경 가중
  commits: 500        # 스캔할 최근 커밋 수
```

**알고리즘.**

```
git log --format=%x00%H --name-only -n <commits>
커밋마다 변경 파일 집합 C를 얻는다. |C| > 50 인 커밋은 제외(대량 리팩터링 노이즈).
쌍 (A,B) ∈ C×C 에 대해 co[A][B] += 1
시드 집합 S(모듈·diff·질의 상위)가 있을 때:
    cochange(F) = Σ_{s∈S} co[F][s] / |S|
    score(F) += γ · normalize(cochange(F))     # γ 초기값 1
```

공변경은 **시드 상대적**일 때 의미가 크므로 `--module`/`--diff`/`--about` 모드에서만
적용한다. 전역 맵에는 적용하지 않는다(전역에서는 "자주 바뀌는 파일"이 곧 중요한
파일은 아니다).

**구현 지점.** `core/git.ts`에 로그 파싱과 공변경 행렬, `core/repomap.ts`의 랭킹에
가중 합류. 얕은 클론·이력 없음·git 아님은 조용히 비활성화(축소 가능 코어 원칙).

**검증.** twin에서 정적 참조 상위 20과 공변경 상위 20의 차집합을 뽑아, 사람이 보기에
"관련은 있지만 참조는 없는" 파일이 실제로 등장하는지 확인한다. 그런 사례가 없으면
이 기능은 채택하지 않는다(측정으로 기각할 준비를 하고 시작한다).

**리스크.** 이력이 짧거나 스쿼시 머지만 쓰는 저장소에서는 신호가 약하다 — 커밋 수
임계값(예: 50 미만이면 비활성) 설정.

**규모.** 1~2일.

### 3.5 측정 하네스의 제품화 — `ctxkit eval`

**문제.** `eval/run.mjs`는 이 저장소 안 스크립트일 뿐 **패키지에 포함되지 않는다**.
도입하는 팀은 프로파일 선택을 감으로 해야 한다.

**인터페이스.**

```sh
ctxkit eval --init                       # tasks.yaml 템플릿 생성
ctxkit eval --tasks tasks.yaml \
  --profiles mid,light --models haiku,sonnet \
  --custom "qwen=ollama run qwen3:14b" --module risk --out eval-results.md
```

**설계 결정.** 하네스는 **모델을 호출해 비용을 발생시키는 유일한 명령**이므로, 실행
전 예상 호출 수(프로파일×모델×과제)를 출력하고 `--yes` 없이는 확인을 요구한다.
과제 파일에 `expect_file`(정답이 들어 있는 파일) 필드를 추가해 **포함률**을 모델
호출 없이도 계산할 수 있게 한다 — 무료로 돌릴 수 있는 사전 지표가 생긴다.

**구현 지점.** `eval/run.mjs` → `src/eval.ts`로 이관, `cli.ts`에 명령 추가,
`package.json`의 `files`는 그대로(dist에 포함됨). 기존 스크립트는 얇은 래퍼로 남긴다.

**검증.** 외부 저장소에서 `npx @seanshin/ctx-kit eval --init` → 과제 3개 작성 →
실행이 한 번에 되는지 확인.

**규모.** 1일.

## 4. 설정 스키마와 호환성

v2가 추가하는 필드는 전부 **선택적**이며 `version: 1`을 유지한다. 로더는 알 수 없는
키를 무시하므로 구버전 ctx-kit이 v2 설정을 읽어도 깨지지 않고, v2가 v1 설정을 읽으면
새 기능이 꺼진 채 동작한다.

```yaml
version: 1
ranking:                 # v2 신규(선택)
  cochange: false
  commits: 500
  query_weight: 2        # --about 가중치
profiles: …              # 변경 없음
```

## 5. MCP 표면 변경

도구는 5종을 유지하고 파라미터만 넓힌다(원칙 8).

| 도구 | v2 추가 파라미터 |
|---|---|
| `make_pack` | `about?`(질의), `diff?`(리비전 범위) |
| `get_module_context` | `about?` |
| `get_repomap` | 변경 없음 |
| `get_rules` | 변경 없음 |
| `search_symbol` | 변경 없음 |

`make_pack`의 설명문에 "약한 모델에게 넘길 컨텍스트를 **과제에 맞춰** 준비한다"는
용법을 추가해, 프론티어 에이전트가 핸드오프 시 질의를 함께 넘기도록 유도한다.

## 6. 비목표 (의도적으로 하지 않는 것)

- **임베딩·벡터 검색 도입.** 무거운 의존성과 인덱스 상태가 생겨 무의존·오프라인·
  "파일이 바닥" 원칙이 동시에 깨진다. 측정상 랭킹+예산으로 충분했고, 의미 검색이
  필요하면 Serena를 나란히 등록하는 기존 답이 있다.
- **Serena 래핑.** 두 MCP 서버는 클라이언트에서 합쳐진다.
- **LLM으로 규칙 자동 작성.** 138개 저장소 연구가 성능 저하를 보고했다. `init --auto`가
  하는 "manifest에서 읽어낸 사실만 채우기"가 안전한 상한이다.
- **웹 UI·대시보드·호스팅 서비스.** 이 도구의 소비자는 사람이 아니라 모델이다.

## 7. 순서와 성공 기준

| 순위 | 항목 | 성공 기준(측정 가능) | 규모 |
|---|---|---|---|
| 1 | `--about` 질의 팩 | 정답 파일 포함률 ≥ 90%, 미사용 대비 상승; 회귀 0 | 반나절 |
| 2 | 규칙·설정 부패 탐지 | 주입한 부패 100% 검출, 실전 2곳 오탐 0 | 반나절 |
| 3 | `--diff` 팩 | 변경 파일 포함률 100%, 예산 내 | 반나절 |
| 4 | 공변경 랭킹 | 참조가 놓친 결합 파일이 상위 20에 등장(없으면 기각) | 1~2일 |
| 5 | `ctxkit eval` 승격 | 외부 저장소에서 명령 하나로 매트릭스 재현 | 1일 |
