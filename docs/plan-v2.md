## 0-B. v2.1 → v2.2 검토 로그 (구현자 관점 정밀 검토)

각 명세를 "지금 이 코드베이스 위에서 실제로 구현 가능한가"로 검토하고 **시제품을
돌려 수치를 얻어** 교정했다. 주요 발견:

1. **중복 검사는 소박하게 만들면 전부 노이즈다.** twin에서 이름이 겹치는 심볼이
   **129건**인데 상위가 `api`(33) `_AI`(25) `__init__`(23) `json`(13) — 전부 정상
   코드다. 필터 체인을 실측해 129 → 56(테스트 제외) → 30(최상위 정의만) →
   26(4자↑·던더 제외) → **12(시그니처 동일)** 로 좁혔고, 남은 12건에는 실제
   중복(`secret`·`hmacHex`가 route/session/middleware 3파일에 각각 재정의)이 들어
   있다. §4.2의 임계값은 이 실측에서 나왔다.
2. **그 필터에는 들여쓰기 정보가 필요한데 추출기가 안 준다.** "최상위 정의만"이
   56→30으로 절반을 걷어내는 가장 강한 필터인데, `CodeSymbol`에 들여쓰기가 없다.
   추출기에 `topLevel` 필드 추가가 §4.2의 선행 조건이다.
3. **추출기 결함을 하나 찾아 고쳤다(0.2.2).** 타입 주석이 붙은 const —
   `export const fn: Handler = (x) => x` — 가 **전혀 추출되지 않았다.** TS
   코드베이스에서 매우 흔한 형태라 해당 파일의 참조 크레딧이 통째로 누락됐다.
   수정 + 테스트 추가(타입 주석 허용, `export const`는 `const` 종류로 별도 포착).
4. **고아 검사는 "심볼 0개 파일"을 고아로 보면 안 된다.** 추출 실패와 미사용을
   구분할 수 없기 때문이다(twin 22/308, ctx-kit 2/19가 심볼 0개). 이 규칙을
   §4.2에 명시. 실측 오탐률: 필터 후 twin 6%, ctx-kit 16%.
5. **import 해석 전략이 비어 있었다.** "`src/ui/**`는 `src/db/**`를 import 못
   한다"를 검사하려면 `../db/client` 같은 지정자를 **파일 경로로 해석**해야 한다.
   §4.2에 2단계 전략(원문 지정자 매칭 + 상대 경로 해석)과 한계를 명시.
6. **BM25 필드 가중을 "반복 삽입"으로 근사한 것은 틀렸다.** 본문이 길면 경로·심볼
   신호가 묻힌다. 필드별로 따로 점수를 내 가중합하는 방식으로 교체(§4.4).
7. **한국어 질의**는 열린 질문이 아니라 **CJK 바이그램**이라는 표준 해답이 있다
   (Lucene CJKAnalyzer 방식). §4.4에 반영.
8. **기존 저장소에 제약을 켜면 첫날부터 빨간불**이라 아무도 안 켠다. 린터들이
   쓰는 **베이스라인(래칫)** 개념을 §4.2에 추가.
9. **`--run-commands`는 코드 실행 벡터**다(적대적 저장소의 AGENTS.md). 보안
   경계를 §10에 명시.
10. 그 밖에 규칙 부패 추출 시 **코드 펜스 제외**, git 명령의 정확한 플래그
    (`--no-merges`·`--diff-filter=d`·`--find-renames`), 공변경 행렬의 메모리
    최적화(시드 열만 누적), 성능 예산, 열화 매트릭스, 테스트 계획, 릴리스 계획을
    추가했다.

- Agentless의 계층적 위치 찾기(파일→함수→편집 지점)가 4계층과 같은 구조 —
  설계 정당성 확보.
- ETH의 AGENTS.md 연구가 "부패한 규칙 = 비용만 내는 규칙"을 뒷받침 — 규칙 부패
  탐지의 우선순위 상향.
- 아키텍처 피트니스 함수(dependency-cruiser·import-linter) 계열이 (A)축의 확립된

**v2.1의 변경**: (A)축을 1급 항목으로 승격(§4.2), `eval`을 1순위로 이동(판정 수단
먼저), `--about`을 BM25 기반으로 개정, 로컬 LLM 실측을 로드맵 정식 항목으로,
항목마다 외부 근거를 명시.

## 1. 진단

측정 전 라운드([findings.md](../eval/findings.md))에서 성패를 가른 것은 **필요한
파일이 팩 안에 있었는가** 하나였다. q2 통과는 `pdm.py`가 우연히 랭킹 1위였기
때문이고, q1 실패는 `his.py`가 모듈 밖이었기 때문이다(4차: 모듈 팩 0/4 vs 저장소
전체 팩 4/4). v1의 선별은 **정적이고 과제와 무관**하다.

두 번째: **저장소 자체의 건강을 아무도 보지 않는다.** `check`의 4항목은 전부
컨텍스트 산출물(규칙 길이·동기화·맵 신선도·시크릿)이다. AI가 써 내려가는 코드가
규칙을 지키는지, 같은 기능이 두 번 구현되는지, 관리되지 않는 영역이 자라는지는
검사 대상이 아니다. 이것이 원천 목표의 첫 구절이 요구하는 것이다.

세 번째: 규칙(Tier 0)은 모든 프로파일에 주입되므로 **부패의 파급이 가장 크다**.
ETH 연구는 컨텍스트 파일이 비용을 20% 올리면서 성능을 못 올리는 조건을
보여줬는데, 사실이 아니게 된 규칙이 바로 그 조건이다.

## 2. 설계 원칙 추가

기존 6원칙(백서 §3)에 더한다.

7. **컨텍스트는 과제 형태를 띤다.** 선별 기준은 `중요도`에서 `중요도 × 과제
   관련도`로. (참고: Agentless의 계층적 위치 찾기, aider의 편집 파일 기준 개인화)
8. **도구 수는 늘리지 않는다.** MCP 도구 5종 유지, 기능은 파라미터로. (참고:
   SWE-agent ACI — 단순성·간결성·가드레일)
9. **저장소 건강은 컨텍스트와 같은 게이트에서 검사한다.** 별도 도구가 아니라
   `check`의 항목으로 — 커밋 시점에 규칙 준수와 드리프트가 함께 잡혀야 "관리"다.

## 4. 항목별 설계

### 4.1 측정 하네스의 제품화 — `ctxkit eval` (1순위: 판정 수단 먼저)

**문제.** `eval/run.mjs`는 패키지에 포함되지 않아 도입 팀은 프로파일을 감으로
고른다. 그리고 이후 항목(§4.4 등)의 채택/기각을 판정할 지표가 제품에 없다.

**인터페이스.**

```sh
ctxkit eval --init                        # tasks.yaml 템플릿
ctxkit eval --tasks tasks.yaml --dry-run  # 모델 호출 없이 포함률만 (무료)
ctxkit eval --tasks tasks.yaml --profiles mid,light --models haiku,sonnet \
  --custom "qwen=ollama run qwen3:14b" --module risk --out results.md
```

**설계.**
- 과제에 `expect_file`(정답이 들어 있는 파일) 필드를 추가한다. `--dry-run`은
  프로파일별 팩을 만들어 포함 여부만 계산한다 — 모델 호출 없는 무료 사전
  지표이며, 검색 단계를 따로 채점하는 RepoBench-R의 축소판이다.
- **포함률은 한 숫자가 아니라 두 숫자다.** 4차 측정에서 드러난 구분(구조 질문 vs
  세부 질문)이 그대로 지표가 된다:
  `outline_hit` = 정답 파일이 맵(개요)에 등장했는가 → 구조 질문에 답할 수 있는가.
  `content_hit` = 정답 파일의 **원문**이 팩에 실렸는가 → 세부 질문에 답할 수 있는가.
  `mid` 프로파일은 원문 섹션이 없으므로 `content_hit`이 0인 것이 정상이며, 이
  구분이 없으면 프로파일 간 비교가 무의미해진다.
- 모델을 호출하는 유일한 명령이므로 실행 전 예상 호출 수(프로파일×모델×과제)를
  출력하고 `--yes` 없이는 확인을 받는다.
- 결과 표에 컨텍스트 토큰·소요 시간·답변 발췌를 남긴다(현행 유지).

**구현 지점.** `eval/run.mjs` → `src/eval.ts` 이관, `cli.ts` 명령 추가. 기존
스크립트는 얇은 래퍼로 남긴다.

**검증.** 외부 저장소에서 `npx @seanshin/ctx-kit eval --init` → 과제 3개 →
`--dry-run` → 실행이 한 번에 되는지.

**참고.** RepoBench-R, CodeRAG-Bench(검색 방식 A/B 방법론). · **규모** 1일.

### 4.2 저장소 건강 검사 — (A)축 (2순위)

**문제.** AI가 쓴 코드가 규칙을 지키는지, 드리프트가 쌓이는지 아무도 보지 않는다.

**인터페이스.** 새 명령이 아니라 `check`의 항목이다(원칙 9). 설정에 선언한다:

```yaml
constraints:                                   # v2.1 신규(선택)
  - id: discount-single-source
    symbol: "apply_discount"                   # 이 심볼의 정의는
    only_in: ["src/pricing/discount.py"]       #   여기에만 있어야 한다
  - id: no-db-from-ui
    from: ["src/ui/**"]                        # 이 경로의 파일은
    must_not_import: ["src/db/**"]             #   저기를 import하면 안 된다
  - id: no-secrets-in-config
    forbid_pattern: "password\\s*="            # 이 패턴이 나타나면 안 된다
    in: ["config/**"]
health:
  duplicates: warn        # 중복 정의 심볼 (기본 warn)
  orphans: warn           # 외부 참조 0인 소스 파일 (기본 warn)
  coverage: info          # 어느 모듈에도 속하지 않는 파일 (기본 info)
```

**알고리즘.**

**(1) 제약 준수.** 세 종류만 지원한다.

- `only_in` — 심볼 정의 위치. 기존 추출기 결과에서 해당 이름의 정의를 모아 허용
  경로 밖이면 위반. *한계*: 추출기는 파일당 50개까지만, 정규식 기반이라 중첩·동적
  정의를 놓친다 → **거짓 통과는 가능하고 거짓 실패는 드물다**는 성질을 문서화한다.
- `must_not_import` — 경로 간 import 금지. **해석 전략 2단계**:
  ① *원문 지정자 매칭* — `from ../db/client`, `from twin.db import x`의 지정자
  문자열을 금지 패턴과 직접 대조(별칭·bare 지정자까지 잡히지만 오탐 여지).
  ② *상대 경로 해석* — `./`·`../`로 시작하면 경로 산술 + 확장자 탐침
  (`.ts .tsx .js .py …`) + `index.*`/`__init__.py` 보정으로 실제 파일에 매핑해
  대조. tsconfig `paths`·모노레포 워크스페이스 별칭은 **해석하지 않는다**(①로만
  잡힌다) — 이 한계를 오류 메시지에 함께 출력한다.
  정밀도가 필요하면 dependency-cruiser·import-linter 어댑터로 넘긴다.
- `forbid_pattern` — 지정 경로 내 정규식 금지(예: 설정 파일의 평문 비밀번호).

**(2) 중복 구현 — 실측으로 교정된 필터 체인.** 소박한 "같은 이름"은 twin에서
129건이 나오고 상위가 전부 정상 코드(`api` 33, `__init__` 23)다. 다음 순서로
좁힌다(괄호는 twin 실측 잔존 수):

```
같은 이름이 2개 이상 파일에 정의        (129)
  → 테스트 경로 제외                     (56)
  → 최상위 정의만 (indent == 0)          (30)   ← 가장 강한 필터
  → 이름 4자 이상 · 던더(__x__) 제외      (26)
  → 시그니처(공백 제거) 완전 일치         (12)   ← 보고 대상
```

남은 12건에 실제 중복이 들어 있다: `secret`·`hmacHex`가 `route.ts`·`session.ts`·
`middleware.ts`에 각각 재정의. 시제품을 ctx-kit 자신에게 돌리면 정확히 1건
(`escapeRegExp`가 `mcp.ts`·`repomap.ts`에 중복)이 나온다 — 신호 대 잡음이
`warn` 수준으로는 충분하다는 증거.

> **선행 조건**: 이 체인의 핵심인 "최상위 정의만"을 쓰려면 `CodeSymbol`에
> `topLevel: boolean`(선행 공백 0 여부)이 필요하다. 추출기에 필드 추가가 §4.2의
> 첫 커밋이다.

**(3) 고아 파일.** 외부 참조 0인 소스 파일. 다음을 제외한다:
테스트 경로 · 엔트리포인트(`main|index|cli|app|__main__|server|worker|setup|conftest`,
Next.js의 `page|layout|route|middleware`) · **심볼이 0개로 추출된 파일**.
마지막 항목이 중요하다 — 추출 실패와 미사용을 구분할 수 없으므로 판단을 보류해야
한다(twin 22/308, ctx-kit 2/19가 심볼 0개). 실측 잔존율: twin 6%(19/308),
ctx-kit 16%(3/19). 설정 `health.orphan_ignore` 글롭으로 추가 예외를 둔다.

**(4) 커버리지.** `modules` 글롭에 하나도 안 걸리는 소스 파일 = 관리되지 않는
영역. `modules`가 비어 있으면 건너뛴다.

**수준과 도입 경로.** 제약 위반은 `fail`, 중복·고아는 `warn`(실전 오탐률을 본 뒤
승격 여부 결정), 커버리지는 `info`.

**베이스라인(래칫).** 기존 저장소에 제약을 켜면 첫날부터 기존 위반으로 게이트가
빨간불이 되고, 그러면 아무도 켜지 않는다. 린터들이 쓰는 방식을 따른다:

```sh
ctxkit check --update-baseline   # 현재 위반을 docs/generated/baseline.json에 기록
ctxkit check                     # 베이스라인에 없는 새 위반만 fail
ctxkit check --no-baseline       # 전량 검사(정리 작업용)
```

베이스라인 항목은 `{검사, 식별자, 위치}`로 저장하고, 위반이 사라지면 다음
`--update-baseline`에서 자동으로 빠진다(줄어들기만 하는 래칫).

**규칙 문서와의 연결.** AGENTS.md의 Constraints 절에 `<!-- ctxkit:constraint
discount-single-source -->` 주석을 달면 `check`가 문서의 제약이 설정에 실제로
등록돼 있는지도 확인한다 — 문서상 규칙과 검사되는 규칙의 괴리를 막는다.

**구현 지점.** `core/check.ts`에 항목 4종, `core/config.ts`에 스키마,
`core/baseline.ts`(읽기·쓰기·대조), 언어별 import 파싱은 `adapters/imports.ts`,
`adapters/symbols.ts`의 `CodeSymbol`에 `topLevel` 추가.

**검증.** 픽스처에 위반을 인위 주입해 100% 검출, ctx-kit·실전 저장소에서 오탐률
측정. 실전 저장소의 AGENTS.md 제약("할인 배율은 discount.py에만" 류)을
`constraints`로 옮겨 실제로 잡히는지 확인.

**참고.** dependency-cruiser(MIT), import-linter(BSD-2), ArchUnit(참고만) — 피트니스
함수 계열; jscpd·knip·vulture — 정밀 어댑터 후보. · **규모** 1~1.5일.

### 4.4 질의 기반 팩 — `--about` (4순위, §4.1 지표로 판정)

**문제.** "할인 계산을 고쳐줘"에도 팩은 저장소 상위 파일을 준다.

**인터페이스.**

```sh
ctxkit pack --about "gold tier 할인 배율" [--profile light] [--module risk]
```
MCP: `make_pack`·`get_module_context`에 `about?` 파라미터(도구 수 불변).

**알고리즘 (v2.0 → v2.2 두 차례 교정).** 임의 가중치 대신 **BM25**를 쓴다 —
SWE-bench 계열에서 파일 수준 위치 찾기의 검증된 기준선(Top-30 재현율 87.7%)이다.

v2.1은 필드 가중을 "경로 3회·심볼명 2회 반복 삽입"으로 근사했는데 **이는 틀렸다**:
반복은 문서 길이 |D|를 함께 키우고, 본문이 긴 파일에서는 경로·심볼 신호가 길이
정규화에 묻힌다. 필드별로 따로 점수를 내 가중합한다(BM25F의 단순형):

```
필드 f ∈ {path, symbols, body},  가중 w = {path: 3, symbols: 2, body: 1}
terms ← tokenize(질의)
bm25_f(F) ← Σ_t idf(t)·tf_f(t,F)·(k1+1) / (tf_f(t,F) + k1·(1−b+b·|F_f|/avg|·_f|))
            k1 = 1.2, b = 0.75 (path·symbols는 길이 편차가 작아 b = 0.5)
idf(t)    ← max(0, ln((N − df + 0.5) / (df + 0.5) + 1))        # 음수 idf 방지
q(F)      ← Σ_f w_f · bm25_f(F)
score(F)  ← normalize(ref(F)) + W · normalize(q(F))            # W 초기 2
```

**토큰화.** 공백·구두점 분리 + `camelCase`/`snake_case`/`kebab-case` 분해(질의와
식별자 양쪽에), 소문자화, 2자 미만·불용어 제거. **CJK는 바이그램**으로 색인한다 —
한국어 "할인 배율"을 `할인`, `인배`, `배율`처럼 2글자 창으로 자르는 방식으로,
형태소 분석기 없이 조사 변화("할인율을" vs "할인율")를 흡수하는 Lucene
CJKAnalyzer의 표준 기법이다. 이로써 v2.1의 열린 질문 하나가 닫힌다.

질의가 없으면 v1과 동일(회귀 없음).

**구현 지점.** `core/retrieve.ts`(토큰화 + 필드별 BM25, 무의존 ~120줄),
`core/repomap.ts`의 `rankFiles(config, files?, query?)`, `core/pack.ts` 헤더에
`about="…"` 기록.

**부수 기능 — `--explain`.** 가중치가 셋(참조·질의·공변경)이 되면 "왜 이 파일이
빠졌나"를 설명할 수 없으면 튜닝이 불가능하다. `ctxkit pack --about … --explain`은
상위 20개 파일의 점수 분해(참조/질의/공변경/최종·포함 여부)를 표로 출력한다.
사용자 튜닝 수단이자 우리 자신의 디버깅 수단이다.

**검증 — 채택/기각 기준.** §4.1 `--dry-run` 포함률로 판정한다. 목표: 질의 관련
과제에서 정답 파일 포함률 ≥ 90%, `--about` 미사용 대비 유의한 상승. 4차 측정의
q1(모듈 밖 심볼)이 `--module risk --about "request_memo"`로 회복되는지가 대표
사례. 상승이 없으면 이 기능은 넣지 않는다.

**참고.** BM25(Robertson & Zaragoza 2009), SWE-bench BM25 기준선, Agentless 위치
찾기, aider 개인화 맵. · **규모** 반나절(+BM25 구현 반나절).

### 4.5 변경 중심 팩 — `--diff` (5순위)

**인터페이스.** `ctxkit pack --diff HEAD~3` · `--diff --staged` · `--diff origin/main...`

**알고리즘.** 시드 = 변경된 소스 파일. 확장 = 시드 심볼을 참조하는 파일 상위 10.
시드는 예산을 넘겨도 **자르지 않고 경고와 함께 전부 포함**(변경 파일이 빠진 리뷰
컨텍스트는 무의미). 거대 diff는 시드 경로 목록 + 상위 원문만 담는 열화 모드.
헤더에 범위·시드 기록.

**git 호출 정확도** (v2.2 보완 — 여기서 틀리면 조용히 잘못된 팩이 나온다):

| 입력 | 명령 |
|---|---|
| `--diff <범위>` | `git diff --name-only --diff-filter=d --find-renames <범위>` |
| `--diff --staged` | `git diff --cached --name-only --diff-filter=d --find-renames` |
| `--diff origin/main...` | 세 점 표기를 그대로 전달(머지 베이스 기준 — 의도된 PR 범위) |

`--diff-filter=d`로 **삭제된 파일을 제외**한다(읽을 수 없어 예외가 난다).
`--find-renames`로 이름 변경을 추적해 같은 파일이 추가+삭제로 중복되지 않게 한다.

**구현 지점.** 새 `core/git.ts`(diff 목록·저장소 판별·§4.7 공용), `core/pack.ts`.
**검증.** 변경 파일 포함률 100%, 확장 파일이 실제 호출자인지 표본 확인.
**참고.** aider의 편집 파일 기준 맵 개인화. · **규모** 반나절.

### 4.7 공변경 랭킹 (7순위, 기각 조건 있는 실험)

**설정.** `ranking: { cochange: false, commits: 500 }` (기본 꺼짐).

**알고리즘.** `git log --no-merges --format=%x00%H --name-only -n N` → 커밋별 변경
집합 C(|C| > 50이면 대량 리팩터링으로 보고 제외) → 공변경 계수. 시드 집합
S(모듈·diff·질의 상위)가 있을 때만
`score(F) += γ·normalize(Σ_{s∈S} co[F][s]/|S|)`, γ 초기 1. 전역 맵에는 미적용.

`--no-merges`가 필요한 이유: 머지 커밋은 `--name-only`에서 기본적으로 빈 목록을
내지만 옵션 조합에 따라 전체 파일을 쏟아내 행렬을 오염시킨다.

**메모리.** 전체 N×N 행렬은 파일 5,000개 저장소에서 비현실적이다. 공변경은 **시드
상대적으로만 쓰므로 시드 열만 누적**한다 — `co[F][s]`에서 `s ∈ S`인 것만 유지해
메모리가 O(파일 수)로 떨어지고 1회 스캔으로 끝난다.

**채택/기각.** 실전 저장소에서 정적 참조 상위 20과 공변경 상위 20의 차집합에
"관련은 있지만 참조는 없는" 파일(설정↔코드, 스키마↔마이그레이션, 문서↔구현)이
실제로 나타나면 채택, 아니면 기각. 얕은 클론·이력 50커밋 미만은 자동 비활성.

**참고.** Zimmermann et al. 2004/2005(ROSE — 프로그램 분석이 못 잡는 결합),
Tornhill(핫스팟·시간적 결합; code-maat은 GPL이라 코드 차용 금지). · **규모** 1~2일.

## 6-B. 성능 예산

`check`는 **pre-commit 훅에서 돌기 때문에** 느려지면 사람들이 훅을 끈다. 이것이
가장 강한 성능 제약이다. 현재 실측: 소스 308개 저장소에서 전체 팩 생성 2.6초,

| 작업 | 저장소 규모 | 예산 | 근거·대책 |
|---|---|---|---|
| `check` 전체 | ~300 소스 | **< 2초** | 훅 체감 한계. 랭킹을 1회만 계산해 검사들이 공유 |
| `check` 전체 | ~5,000 소스 | < 10초 | 초과 시 건강 검사는 `--full`에서만, 훅은 규칙·부패만 |

| `pack --diff` | 임의 | < 3초 | git 호출 1회 + 시드 확장만 |
| 공변경 스캔 | 500 커밋 | < 3초 | 1회 스캔·시드 열만 누적. 결과는 `docs/generated/`에 캐시하고 HEAD가 바뀌면 무효화 |

## 7. 비목표

## 10. 보안 경계

새 기능 중 둘이 신뢰 경계를 건드린다. 저장소는 **신뢰할 수 없는 입력**일 수 있다
(클론한 남의 코드).

- **`check --run-commands`는 코드 실행이다.** AGENTS.md의 `## Commands` 절에 적힌
  명령을 실행하므로, 적대적 저장소가 임의 명령을 실행시킬 수 있다. 따라서:
  기본 꺼짐 · `init --ci`/`init --hooks`가 만드는 템플릿에 **절대 넣지 않는다** ·
  실행 전 실행할 명령 목록을 출력 · `## Commands` 절 밖의 백틱은 후보로 삼지
  않는다 · 문서에 "신뢰하는 저장소에서만" 명시.
- **`--diff`·공변경은 git 호출**이다. 사용자 입력(리비전 범위)이 명령줄에 들어가므로
  셸을 거치지 않고 `spawnSync(cmd, args)` 배열 인자로만 전달한다(셸 인젝션 차단).
- 기존 시크릿 스캔은 유지된다 — 새 산출물(`baseline.json`, `--explain` 출력)도
  LLM에 붙여넣어질 수 있으므로 **스캔 대상에 포함**한다.
