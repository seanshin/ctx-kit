## 1. 요약

AI로 개발되는 저장소는 능력이 근본적으로 다른 모델들이 함께 소비한다 — 도구로
탐색하는 프론티어 에이전트, 32~128K 윈도의 중형 모델, 프롬프트 한 번이 전부인
소형 로컬 LLM. 한 가지 소비 방식만 가정한 도구는 나머지를 놓친다.

ctx-kit은 프로젝트 컨텍스트의 단일 원본을 유지하고 거기서 각 모델 계층이 쓸 수
있는 형태를 파생시켜 3가지 인터페이스(MCP 서버, CLI, 일반 파일)로 제공한다.
합성 픽스처와 소스 308개 실전 저장소의 통제 측정에서, 과제 성패를 가른 것은
**모델 등급이 아니라 컨텍스트 형태**였다: 구현 세부 과제는 파일 원문이 없으면
모든 모델 계층에서 실패했고 있으면 모든 계층에서 통과했다. 별도의 실사용
시험에서 프론티어 에이전트는 같은 질문들을 벌크 컨텍스트 없이 표적 MCP 호출
2회, 9.3초에 해결했다 — 이질적인 모델 집합에게 코드베이스를 읽히게 하는 것은
하나의 "최적 컨텍스트 덩어리"가 아니라 계층화라는 증거다.

## 2. 문제

### 2.1 모델 이질성은 항구적이다

비용·프라이버시·지연 때문에 소형 로컬 모델은 프론티어 에이전트와 같은
코드베이스에서 계속 함께 쓰인다. 이들은 정도가 아니라 종류가 다르다:

| 소비자 | 상호작용 방식 | 잘못 제공했을 때의 실패 양상 |
|---|---|---|
| 프론티어 에이전트 | 다중 턴, 도구 호출 | 컨텍스트 비대 — 필요하면 가져왔을 토큰까지 선지불 |
| 중형 모델 | 1회 로드, 약한 도구 사용 | 구조 실명 — 이름은 알지만 내용을 모름 |
| 소형 로컬 LLM | 붙여넣은 프롬프트 1회 | 잘림 — 필요한 파일이 조용히 사라짐 |
| 챗창의 사람 | 복사·붙여넣기 | 붙여넣을 산출물 자체가 없음 |

### 2.2 컨텍스트 파일이 대규모로 잘못 쓰이고 있다

138개 저장소를 대상으로 한 공개 평가에서, LLM이 생성한 에이전트 지침 파일은
과제 성공률을 *낮추면서* 추론 비용을 20% 이상 올렸다. 문제는 표준이 아니라
내용이다 — 생성된 규칙 파일은 린터가 강제하는 것을 반복하고, 에이전트가 이미
볼 수 있는 파일 목록을 나열하며, 정작 중요한 두세 가지 사실을 파묻는다. 규칙
작성을 자동화하는 시스템은 반드시 길이를 제약하고 내용을 "코드가 표현할 수
없는 것"으로 한정해야 한다.

### 2.3 도구 종속은 피할 수 있다

Linux Foundation에 이관되어 Claude Code·Codex CLI·Cursor·Aider·Copilot·
Gemini CLI·Windsurf가 네이티브로 읽는 AGENTS.md 표준과 MCP가 벤더 중립 설계를
현실화했다. 여기서 중립성은 이상론이 아니다 — 하나의 저장소가 §2.1의 모델
집합을 진실의 사본 N개 없이 섬길 수 있게 하는 유일한 조건이다.

## 3. 설계 원칙

1. **단일 원본(SSOT).** 규칙은 `AGENTS.md`에만 있고 도구별 파일은 생성 표식이
   붙은 사본 또는 심링크다. ctx-kit이 만들지 않은 파일은 명시적 `--force`
   없이 절대 덮어쓰지 않는다.
2. **코드가 말할 수 없는 것만 적는다.** 명령·제약·불변식·용어집. 150줄 상한은
   관례가 아니라 게이트가 강제한다.
3. **사람 작성과 파생 산출물의 엄격한 분리.** 맵과 팩은 코드에서 재생성하며
   손대지 않는다. 게이트가 신선도를 검사해 둘이 조용히 어긋나지 않게 한다.
4. **능력 프로파일.** 모델 계층마다 어떤 섹션을 어떤 토큰 예산으로 주입할지
   선언 하나로 정한다 — 새 계층 지원은 코드 변경이 아니라 설정 변경이다.
5. **파일이 바닥이다.** 모든 기능은 일반 파일 산출물을 남긴다. MCP도 CLI도
   없는 환경(챗창에 붙여넣는 사람 포함)까지 지원된다.
6. **축소 가능 코어.** 외부 도구가 하나도 없어도 전부 동작한다. 외부 연동은
   선택적 가속기이지 의존성이 아니다.

## 4. 아키텍처

### 4.1 컨텍스트 4계층

| 계층 | 내용 | 생산자 | 갱신 | 대략 비용 |
|---|---|---|---|---|
| 0 | `AGENTS.md`: 운영 규칙 | 사람 | 변경 시 | 200~600 tok |
| 1 | 리포맵: 랭킹된 파일 + 심볼 아웃라인 | 자동 생성 | 커밋/CI | 2~8K tok |
| 2 | 모듈 문서 + 모듈 팩 | 사람 + 생성 | 필요 시 | 5~45K tok |
| 3 | 심볼 검색(정의 + 참조) | 실시간 | 실시간 | 질의당 100~800 tok |

계층은 토큰 대비 정보량 순이다. 프론티어 에이전트는 0계층과 3계층에 살아야
하고, 소형 로컬 모델은 2계층으로만 섬길 수 있다.

### 4.2 소비 프로파일

```yaml
profiles:
  frontier: { inject: [agents], budget: 4000 }
  mid:      { inject: [agents, repomap], budget: 24000 }
  light:    { inject: [agents-summary, repomap, target-files], budget: 12000 }
```

`light` 팩은 규칙을 앞에 놓고 압축한 리마인더를 뒤에 반복한다. 이는 긴
컨텍스트 모델의 잘 알려진 "중간에서 길을 잃는" 회상 패턴에 대한 의도적
대응이다 — 회상률이 가장 높은 두 위치가 프롬프트의 머리와 꼬리이므로, 가장
어겨지기 쉬운 제약을 양쪽에 배치한다.

### 4.3 코어 하나에 인터페이스 셋

```
        ┌─────────────────────────────────────────────┐
        │  A. MCP 서버 (stdio)   — 도구 5종            │  에이전트형 클라이언트
        ├─────────────────────────────────────────────┤
        │  B. CLI               — 명령 7종            │  터미널·훅·CI
        ├─────────────────────────────────────────────┤
        │  C. 파일              — docs/generated/     │  그 외 전부
        └─────────────────────────────────────────────┘
                        │
                     공통 코어
        config · walk · rank · pack · sync · check · detect
```

A는 `get_rules`, `get_repomap`, `get_module_context`, `search_symbol`,
`make_pack`을 노출한다. `make_pack`은 특기할 만하다 — 프론티어 에이전트가
세션을 떠나지 않고 *더 약한 모델을 위한* 컨텍스트를 준비하게 해주며, 이
핸드오프가 혼합 모델 운용을 실용적으로 만든다.

## 5. 알고리즘

### 5.1 심볼 추출

TypeScript/JavaScript, Python, Go, Rust, JVM 계열, Ruby, PHP, Swift, C/C++에
대해 언어별 정규식 아웃라인으로 정의(종류·이름·시그니처·줄번호)를 추출하며
파일당 50개로 제한한다. 파서보다 의도적으로 얕다 — 무의존이고 오프라인에서
돌며, 랭킹·패킹 코드를 건드리지 않고 tree-sitter 어댑터로 교체 가능한
인터페이스 뒤에 있다. 의미론적 분석은 Serena에 명시적으로 위임하며(§9),
`search_symbol`의 도구 설명이 에이전트에게 그 사실을 알린다.

### 5.2 리포맵 랭킹

맵은 "무엇부터 볼 것인가"에 답해야 하므로 알파벳순이 아니라 중요도가 필요하다.
ctx-kit은 각 파일이 정의한 심볼이 *다른* 파일에서 참조된 횟수로 점수를 매긴다.
aider의 tree-sitter+PageRank 접근의 무의존 단순화이며, 알고리즘 참고만 했고
코드 차용은 없다(aider는 Apache-2.0):

```
파일 F와 그 심볼 S(F)에 대해:
    S(F)의 각 심볼 s에 대해:
        건너뜀: 이름 길이 < 4 또는 흔한 단어(main, data, get …)
        다른 각 파일 G에 대해:
            score(F) += min(G에서 s의 단어경계 일치 수, 20)
    score(F) += min(|S(F)|, 10) * 0.5        # 상한 있는 자체 가중
    F가 테스트 경로면: score(F) *= 0.2         # 프로덕션 코드 우선
점수 내림차순 정렬 → 토큰 예산이 소진될 때까지 아웃라인 출력
```

세 가지 가드는 각각 실전 저장소의 실패에서 얻은 것이다(§7): 파일당 일치 상한은
인기 있는 헬퍼 하나의 독점을 막고, 자체 가중 상한은 "작은 정의가 많은 파일"이
"많이 쓰이는 심볼 하나"를 이기지 못하게 하며, 테스트 강등은 스위트 전체가
참조하는 공용 픽스처가 예산을 전부 차지하는 것을 막는다.

### 5.3 팩 조립

팩은 프로파일이 선언한 순서대로 섹션별로 조립되며, 규모가 커져야만 필요성이
드러나는 네 불변식을 지킨다:

- **내장 섹션은 예산의 정해진 지분만 갖는다.** 리포맵은 새로 만들든 캐시에서
  읽든 팩 예산의 ⅓(최대 4000토큰)로 제한된다. 이것이 없으면 12K 팩에 8K 캐시
  맵이 들어가 소스가 들어갈 자리가 사라진다.
- **모듈 팩은 모듈 범위 맵**과 모듈 밖 상위 참조 파일의 경로 색인을 받는다.
  저장소 전체 맵을 재사용하면 산출물에서 가장 비싼 토큰을 과제가 건드릴 수도
  없는 파일에 쓰게 된다. 실전 저장소 측정에서 `risk` 모듈 팩은 이 규칙 전에는
  무관한 프론트엔드 파일 4개를 맵에 싣고 있었고, 이후 자기 소스를 4개 대신
  13개 담았다. 대가는 §6.3에 실측으로 적었다 — 모듈 밖에 정의된 심볼의 위치는
  더 이상 답할 수 없다.
- **예산이 자를 것을 정렬한다.** 대상 파일은 참조 랭킹 순으로 출력되어, 잘림이
  이름순 끝자락이 아니라 가장 덜 참조되는 파일에 떨어진다.
- **안 들어가는 파일은 중단 신호가 아니라 건너뛸 대상이다.** 첫 초과 파일에서
  섹션을 끝내면 뒤에 있는 더 작고 여전히 유효한 파일들의 예산까지 버리게 된다 —
  같은 실전 모듈에서 예산의 45%가 미사용으로 남았다.

전체 의사코드는 [부록 A](#부록-a-팩-조립-의사코드)에 있다.

### 5.4 규칙 배포와 게이트

`sync`는 생성 표식과 함께 도구별 파일을 쓰고, 표식 없는 파일은 덮어쓰기를
거부한다(안내와 함께 exit 1). 이미 손으로 쓴 `CLAUDE.md`가 있는 저장소에서도
"단일 원본"을 안전하게 도입할 수 있게 하는 장치다. `check`는 네 가지 불변식을
강제한다: 규칙 길이, sync 신선도, 맵 신선도(mtime 기반이라 경고 — git
체크아웃은 mtime을 보존하지 않는다), 그리고 LLM으로 향하는 모든 산출물에 대한
시크릿 스캔.

## 6. 평가

### 6.1 방법론

각 측정은 (프로파일 × 모델 × 과제) 셀이다. 하네스는 `ctxkit pack --stdout`으로
컨텍스트를 만들고, `컨텍스트 + 질문`을 stdin을 읽는 모델 명령에 파이프하고,
기대 키워드 일치로 채점한다. 모델 프로세스는 **빈 임시 디렉토리**에서
실행되므로 파일 도구를 가진 모델도 저장소를 읽어 제공된 컨텍스트를 우회할 수
없다 — 이 통제가 없으면 실험은 아무것도 측정하지 못한다. 과제는 프로파일을
판별하도록 고른다: 구조만으로 답할 수 있는 것 하나, 파일 원문이 필요한 것 하나,
규칙이나 호출 구조를 묻는 것 하나.

하네스(`eval/run.mjs`)는 `ollama run <모델>`을 포함해 stdin을 읽는 어떤 명령과도
동작하고 저장소·과제 파일을 인자로 받으므로, 팀이 자기 코드베이스에서 같은
매트릭스를 재현할 수 있다.

### 6.2 결과

**1·2차** — 합성 픽스처, 이어서 소스 308개 실전 저장소. 과제 3개 통과율:

| 프로파일 | 소형 모델 | 상위 모델 | 컨텍스트 크기(2차) |
|---|---|---|---|
| `mid` (규칙+맵) | 2/3 | 2/3 | ~4.3K tok |
| `light` (+랭킹된 파일 원문) | **3/3** | **3/3** | ~8.7K tok |

실패한 셀은 언제나 구현 세부 질문이었고 *두* 모델 계층 모두에서 그랬으며, 파일
원문이 있자 두 계층 모두 통과했다. 실무적 결론은 통념의 역이다 — 약한 모델이
코드베이스 질문에 실패할 때 첫 번째 레버는 더 강한 모델이 아니라 더 잘 구성된
컨텍스트다. 특기할 점: 두 모델 모두 값을 지어내지 않고 "컨텍스트에 없다"고
답했다. 프로파일 경계가 환각이 아니라 정직한 거부를 만들어냈다.

**3차** — 실전 저장소 실사용 에이전트 세션, 파일 읽기 도구 차단, ctx-kit MCP만
제공. 세 질문(명령, 파일+기본값, 프로젝트 규칙)에 **4턴 9.3초, 3/3 정답** —
`get_rules`와 `search_symbol` 한 번이 전부였다. 최소 상시 규칙 + 온디맨드
검색이라는 프론티어 프로파일이 어떤 팩보다 훨씬 적은 토큰을 썼다. 부수 관찰:
`search_symbol`이 정의와 함께 참조 라인을 반환하기 때문에 파일을 열지 않고도
파라미터 기본값이 출력에 실려 나왔다.

### 6.3 모듈 팩 범위화: 실측된 경계

모듈 범위 맵(§5.3) 도입 후 실전 매트릭스를 재실행했다. 모듈 안 과제 두 개는
그대로였지만, 모듈 *밖* 심볼의 정의 위치를 묻는 과제는 네 셀 전부 통과에서
실패로 바뀌었다. 같은 질문을 저장소 전체 팩에 물으면 — 같은 모델, 같은 하네스,
`--module`만 뺀 조건 — **4/4 통과**한다(mid ~4.2K, light ~12.0K 토큰). 따라서
이는 회귀가 아니라 정확한 경계다: **모듈 팩은 자기 모듈 안의 질문에 답하고,
모듈 간 심볼 위치는 3계층이나 저장소 전체 팩의 몫이다.** 네 모델 모두 경로
색인에서 추측하지 않고 "컨텍스트에 없다"고 답했다 — 컨텍스트 시스템이 만들어야
할 실패 양상이다.

### 6.4 데이터가 만들어낸 주의사항

1차에서 두 모델 모두 맵에 호출 정보가 없는데도 호출 관계 질문을 맞혔다 —
시그니처와 이름에서 추론한 것이다. 이는 능력이 아니라 이름 품질에 기댄 요행이며
네이밍이 약한 코드베이스에서는 조용히 실패한다. 호출 관계 질문은 3계층의
몫이고, 이 발견은 성공이 아니라 사용 제약으로 기록한다.

## 7. 실전 저장소가 가르쳐준 것

소스 308개 실전 저장소(Python 백엔드 + TypeScript 프론트엔드, 제외 후 추적
소스 약 200개) 온보딩이 합성 픽스처가 숨겼던 결함 3건을 드러냈다. 각각은 §5의
규칙이자 테스트가 됐다:

1. **공용 픽스처가 랭킹을 독점했다.** `conftest.py`와 테스트 모듈은 스위트 전체가
   참조하므로, 산출물에서 가장 값비싼 토큰인 맵 상위가 테스트 골조로 채워졌다.
   코드베이스를 파악하는 에이전트에게는 프로덕션 코드가 먼저다.
   *조치: 테스트 경로 ×0.2 강등, 자체 정의 가중치 상한.*
2. **캐시된 맵이 팩을 굶겼다.** 12K 팩에 8K 캐시 맵이 통째로 들어가 소스 자리가
   사라졌고, 과제가 필요로 한 파일이 아예 등장하지 않았다.
   *조치: 모든 내장 섹션에 예산 지분 상한.*
3. **잘림이 엉뚱한 파일에 떨어졌다.** 대상 파일이 알파벳순이라 `pdm.py`가
   탈락하고 덜 참조되는 파일이 살아남았다.
   *조치: 참조 랭킹 순 출력으로 잘림이 가장 덜 중요한 파일에 떨어지게.*

일반화하면, 합성 픽스처는 *정확성*을 검증하고 실전 저장소는 *비례*를 검증한다.
이 결함들이 픽스처 규모에서 보이지 않았던 이유는 아무것도 예산 경계 근처에
가본 적이 없었기 때문이다.

## 8. 비용·안전 태세

- **유료 인프라 불필요.** `init --hooks`는 CI와 동일한 게이트를 커밋 시점에
  로컬에서 무료로 실행하는 git 훅을 설치한다. GitHub Actions 워크플로는 선택
  사항이며 비공개 저장소에서 유료 분량을 소모함을 명시한다.
- **필요한 곳의 시크릿 스캔.** `check`는 규칙·모듈 문서·생성 팩에서 개인키
  블록, 클라우드 액세스 키, 토큰형 문자열, `api_key = "…"` 형태 대입을 찾는다.
  이 산출물들이야말로 외부 서비스에 붙여넣어지는 것들이라 가장 값진 검사
  지점이자 가장 잊기 쉬운 지점이다.
- **구조적으로 비파괴적.** `sync`는 표식 없는 파일을 거부하고, `init`은 기존
  파일을 건너뛰며, 어떤 명령도 삭제하지 않는다.
- **완전 로컬.** ctx-kit은 네트워크 호출을 하지 않는다.

## 9. 라이선스 태세

ctx-kit은 MIT다. 외부 도구는 코드 차용 없이 CLI 실행으로만 통합해(어댑터 패턴)
라이선스 경계를 해석의 문제가 아니라 기계적 사실로 유지한다:

| 도구 | 라이선스 | 통합 방식 |
|---|---|---|
| [Repomix](https://github.com/yamadashy/repomix) | MIT | 선택적 패커, CLI 실행 |
| [Serena](https://github.com/oraios/serena) | MIT | 3계층으로 *나란히* 등록, 래핑 안 함 |
| [aider](https://aider.chat/docs/repomap.html) | Apache-2.0 | 알고리즘 참고만, 코드 없음 |
| universal-ctags | GPL | 제외 |

Serena를 뒤가 아니라 옆에 두는 것은 라이선스이자 아키텍처 선택이다 — MCP를
말하는 모든 클라이언트에서 서버 둘은 자연스럽게 합쳐지므로, 래핑은 이득 없이
클라이언트 구현만 늘린다.

## 10. 관련 작업

**AGENTS.md**(Linux Foundation)는 이 프로젝트가 진실의 원본으로 삼는 규칙
파일을 표준화했다. **aider**는 tree-sitter와 PageRank로 랭킹된 리포맵을
개척했고, ctx-kit은 단순화된 랭킹을 독립 구현했다. **Repomix**와
**code2prompt**(둘 다 MIT)는 저장소를 단일 프롬프트로 패킹하며 — 상호 보완적이고
Repomix는 선택적 백엔드로 지원된다. **Serena**(MIT)는 MCP로 LSP급 의미 검색을
제공해 ctx-kit의 아웃라인 추출기가 의도적으로 다루지 않는 영역을 담당한다.
**Ruler** 등은 규칙을 여러 어시스턴트에 배포하며, ctx-kit의 `sync`는 그 공통
부분집합을 무의존으로 내부 구현하고 어댑터 자리를 열어뒀다.

여기서 새로운 것은 개별 구성요소가 아니라 조합이다 — 일급 설정 객체로서의 능력
프로파일, 파일을 보장된 바닥으로 삼는 코어 하나 위의 3인터페이스, 그리고
프로파일 선택을 취향이 아닌 실증의 문제로 만드는 평가 하네스.

## 11. 한계와 로드맵

- **대리 모델.** "소형 모델" 계층은 소형 API 모델을 대리로 측정했다. 진짜 로컬
  LLM 라운드(`--custom "ollama run …"`)는 로컬 설치 후 예정이며 하네스는 이미
  지원한다.
- **의미론이 아닌 어휘적 참조.** 참조 계수는 단어 경계 일치라, 흔한 단어와
  충돌하는 심볼명은 점수가 부풀 수 있다. 짧고 흔한 이름은 걸러내지만 휴리스틱은
  여전히 어휘적이다.
- **아웃라인 수준 심볼.** 정규식 추출은 중첩·동적 정의를 놓친다. tree-sitter
  어댑터 자리가 있다.
- **근사 토큰.** `chars/4`는 예산 판단에 충분하지만 정확하지 않고, 특히
  **CJK 텍스트를 과소평가한다** — 한글·일문·중문은 글자당 1토큰에 가깝다.
  한국어 주석 비중이 큰 코드베이스는 여유를 둘 것. 토크나이저 어댑터가 이
  단서를 없애줄 것이다.
- **실전 온보딩 1건.** 저장소 하나, 언어 쌍 하나. 대형 수작업 규칙 파일을
  AGENTS.md 흐름으로 이관하는 2호 온보딩이 예정돼 있다.

로드맵: 토크나이저 정밀 예산, 진짜 로컬 LLM 측정 라운드, tree-sitter 심볼
어댑터, 온보딩과 함께 기여되는 저장소별 과제 세트.

## 부록 A: 팩 조립 의사코드

```
build_pack(config, profile, module?):
    budget    ← profile.budget
    out       ← header(profile, module, budget)
    reminder  ← ""

    profile.inject의 각 section에 대해:
        case "agents":          out += AGENTS.md 전문
        case "agents-summary":  out += AGENTS.md 앞 40줄
                                reminder ← 앞 12줄            # 꼬리에 덧붙임
        case "repomap":
            cap ← min(budget / 3, 4000)
            map ← tokens(캐시) ≤ cap이면 캐시, 아니면 build_map(cap)
            out += map
        case "target-files":
            files ← rank_files(module ? glob(module) : 전체 소스)
            reserve ← tokens(reminder) + 50
            files의 각 f에 대해:
                block ← "### {경로}\n```{언어}\n{내용}\n```"
                if tokens(out + block) + reserve > budget:
                    out += "…나머지 파일 생략 (예산 N 토큰)"
                    break
                out += block

    if reminder: out += "## Rule Reminder\n" + reminder
    return out, tokens(out)
```

## 부록 B: check 판정 기준

| 검사 | 수준 | 조건 | 근거 |
|---|---|---|---|
| `agents-length` | fail | 없음 또는 150줄 초과 | 장황한 규칙은 실측상 에이전트를 해침(§2.2) |
| `sync` | fail | 도구별 파일 ≠ `AGENTS.md` | 조용한 어긋남은 SSOT를 무력화 |
| `sync` | warn | 도구별 파일 없음 | 저장소에 따라 의도적일 수 있음 |
| `repomap` | warn | 소스가 맵보다 최신 | 체크아웃 후 mtime은 신뢰 불가 |
| `secrets` | fail | 규칙·모듈 문서·팩의 키/토큰/대입 패턴 | 이 산출물들은 기기를 떠남 |

## 부록 C: 측정 재현

```sh
git clone https://github.com/seanshin/ctx-kit && cd ctx-kit
npm install && npm test

# 내장 픽스처
node eval/run.mjs

# 자기 저장소 + 로컬 모델
node eval/run.mjs --fixture /path/to/repo --tasks my-tasks.yaml \
  --module <모듈> --custom "qwen=ollama run qwen3:14b" --out results.md
```

과제 파일 형식:

```yaml
tasks:
  - id: q2-detail
    question: "X의 기본값은? 숫자만 답하라."
    expect: ["180"]          # 답변에 키워드가 하나라도 있으면 통과
```

최소한 하나는 구조만으로 답할 수 있고 하나는 파일 원문이 필요하도록 세트를
설계할 것 — 그 대비가 프로파일 비교를 유의미하게 만든다.
